# RAG·MCP·클라우드 LLM 데이터 흐름

기준일: 2026-10-28 (교수님 피드백 4 대응). 코드를 읽고 실제 요청을 캡처해 확인한 내용이다. 확인하지 않은 부분은 "확인 안 함"으로 표시했다.

## 한 줄 요약

**클라우드 LLM(Gemini)은 이 PC의 DB나 MCP에 접속하지 않는다.** 백엔드(FastAPI)가 같은 PC 안의 MCP 서버를 호출해 기록을 찾고, **찾은 기록을 요청에 담아 Gemini에 한 번 보낸다.** Gemini는 받은 내용만 보고 답한다. 그래서 "클라우드가 로컬 DB를 어떻게 보느냐"의 답은 "보지 않는다, PC가 찾아서 보내 준다"이다.

## "현재 상태 평가하기"가 하는 일 (순서)

| 단계 | 어디서 | 무슨 일 |
|---|---|---|
| 1 | 폰·PC 브라우저 → 백엔드 | 보호자가 질문을 적고 버튼을 누른다. `POST /care/evaluate` |
| 2 | 백엔드(PC) | 평가할 관찰을 고른다: 이번 외출에서 **개 짖음 후보 창이 있는 가장 최근 관찰**(없으면 가장 최근 관찰). 현재 음성 분석 결과와 보호자 의견을 SQLite에서 읽는다 |
| 3 | 백엔드 → **MCP 서버(같은 PC의 자식 프로세스, 표준 입출력)** | 도구 3개를 호출한다: `search_observations`(같은 반려견의 과거 기록 검색), `get_observation_stats`(집계), `get_care_history`(이전 제안·결과). 같은 반려견·평가 시각 이전 기록만 돌려준다. 이어서 `get_outing_facts`로 **이번 외출의 사실(이전 외출에서 보호자가 확인한 기록 포함)**을 가져온다. 관찰 검색만으로는 이전 녹음에 대한 보호자 확인(TV 소리 등)을 볼 수 없기 때문이다 |
| 4 | 백엔드 → **Gemini API(인터넷, HTTPS 1회)** | 요청을 두 부분으로 만들어 보낸다. **시스템 지시**(규칙 문장)와 **유저 메시지**(질문 + 현재 관찰 + 3에서 찾은 기록). API 키는 요청 헤더에만 쓴다 |
| 5 | 백엔드 | Gemini의 답(JSON)을 검사한다: ① 인용한 번호가 현재 관찰·찾은 기록 안에 있는가 ② 현재 음성 분석과 모순되지 않는가. **통과하지 못하면 PC의 규칙 제공자가 대신 만든다** |
| 6 | 백엔드 | 첫 문장("개 짖음 소리 후보가 감지되었습니다" / "…짖음이 없었다는 뜻은 아닙니다")은 **서버가 직접** 쓰고, 제공자가 쓴 후보 유무 문장과 소리 크기 기반 "분당 N회" 문장은 뺀다 |
| 7 | 백엔드 → 화면 | 제안, **"AI에 보낸 내용"**(보낸 그대로), 검색 근거를 저장해 보여 준다 |

화면의 "AI(Gemini)에 보낸 내용" 카드는 4단계에서 **실제로 보낸 시스템 지시와 유저 메시지 전문**을 펼쳐 볼 수 있다. 규칙 제공자가 만든 제안이면 "클라우드로 보낸 내용 없음"이라고 표시한다.

## 외출 전체를 묻는 질문 ("짖은 횟수는 몇 번?")

"현재 상태 평가"는 관찰 하나를 본다. 그래서 같은 질문을 **외출 전체 기록으로도** 답한다(`POST /outings/{id}/explain`).

1. 백엔드가 MCP `get_outing_facts`로 그 외출의 **사실 목록**(서버가 계산한 문장·수치, 번호 포함)을 가져온다.
2. Gemini에는 질문과 사실 목록을 보내 **어떤 사실을 보여 줄지 번호만 고르게** 한다.
3. 화면에 나오는 문장과 수치는 **서버가 사실에서 그대로 붙인다**(Gemini가 새 문장·수치를 만들지 않는다).

예: "YAMNet Bark 모델의 분석 창 25개 중 개 짖음 소리 후보 창은 10개입니다. 5초 창은 정확한 발성 횟수가 아닙니다." — "횟수"가 아니라 **후보 창 수**로 답한다.

## 무엇이 PC 밖으로 나가고, 무엇이 나가지 않는가

| 나가는 것 (Gemini로) | 나가지 않는 것 |
|---|---|
| 질문, 현재 관찰 요약, 찾은 과거 기록(번호·요약·보호자 의견), 반려견 프로필(보호자 입력), 규칙 문장 | 원본 음원·영상, 파일 경로, 접속 키, API 키(헤더로만 사용) |
| (외출 질문) 사실 목록의 문장과 번호 | MCP 서버·DB 자체(클라우드는 접속하지 않음) |

2026-10-28 캡처 확인: 평가 요청 1건(약 9,500자)에 위 항목만 있었고 `.wav`, 오디오 URL, base64, API 키는 없었다.

## "클라우드 LLM이 일반 상식으로만 답하는 것 아닌가?"

- 찾은 기록이 **요청에 실제로 들어간다**(위 캡처로 확인, 기록 5건·번호 포함). 그리고 서버가 **응답이 인용한 번호가 그 기록 안에 있는지** 검사한다.
- **한계(확인된 것):** 검사는 "인용 번호가 허용 범위인가"와 "현재 음성 분석과 모순되지 않는가"까지다. Gemini가 기록의 **수치나 인과를 정확히 옮겼는지는 문장별로 검증하지 않는다.** 블록도 7단계의 상태 표시에도 "인용 범위만 검사, 문장별 수치·인과 검증은 남아 있음"이라고 적혀 있다.
- 외출 질문 경로는 문장과 수치를 서버가 만들기 때문에 이 위험이 없고, Gemini는 번호만 고른다.

## "코드 규칙 기반"(규칙 제공자)이 하는 일

Gemini를 쓰지 않거나(키 없음, 호출 실패, 검사 실패) 때 PC 안의 코드가 만든다. 영상 행동이 없고 음성 분석이 있을 때의 예:

| 입력(음성 분석 + 보호자 의견) | 규칙 제공자의 문장 |
|---|---|
| 의견 "판단 어려움" | 소리 종류를 판단하기 어렵다. 원본을 다시 듣고 주변 소음을 확인해 의견을 보완하라 |
| 후보 있음 + "반려견 소리" | 후보와 확인 의견이 있다. 전후 상황을 기록하고 다음 외출에서도 반복되는지 비교하라 |
| 후보 없음 + "다른 소리/TV" | 후보가 없고 다른 소리라는 의견이다. 이 자료만으로 케어 조치를 권하지 않는다 |
| 후보 없음 + "반려견 소리" | 모델과 확인 의견이 다르다. 놓친 사례인지 원본을 다시 들어 검토하라 |

정해 둔 규칙대로만 말하고 새로운 분석을 하지 않는다.

## 평가 (2026-10-28, 실제 Gemini)

`scripts/evaluate_care_gemini.py`: 합성 기록 + 공개 음원 클립으로 만든 격리 DB에서 질문 10개 × 관찰 2개(후보 있음·없음) = 20건을 실제 Gemini(`gemini-3.5-flash-lite`)로 평가했다. 결과는 [care_gemini_eval_2026-10-28.json](evidence/care_gemini_eval_2026-10-28.json). **개발자가 쓴 질문과 자동 형식·안전 검사이며 사람이 답의 질을 채점한 것이 아니다.** 같은 질문도 호출마다 문장이 달라 다시 돌리면 결과가 조금 달라질 수 있다.

| 시점 | 모든 검사 통과 | 내용 |
|---|---|---|
| 수정 전 | 16/20 | "보호자가 TV라고 확인한 기록이 있어?"와 "지난번과 비교" 질문 4건에서 **기록이 있는데 "찾을 수 없다/없다"고 답함**. 원인: 관찰 검색 경로가 이전 녹음에 대한 보호자 확인(TV 소리)을 보지 못했음 |
| 비교 사실 추가 후 | **5회 반복 99/100** (4회 20/20, 1회 19/20) | 이전 외출이 있으면 서버가 "비교한 값" 또는 "비교하지 않은 이유" 문장을 항상 근거에 넣고, Gemini가 이전 기록이 없다고 쓰면 그 문장을 서버 문장으로 바꾼다. 19/20이었던 1회의 실패는 폴백(실제 Gemini 응답이 아니었음)이며 **당시 원인을 기록하지 않아 모른다**(이후 평가는 실패 원인을 저장한다). 이 반복 평가는 같은 질문 세트에 맞춰 고친 뒤 다시 잰 것이라 **개발 평가**이다 |
| (중간) TV 수정만 한 뒤 | 19/20 | TV 질문은 "이전 외출 관찰 #4에서 보호자 의견 TV·외부 소리"로 정확히 답함. **남은 1건**: 후보 없는 관찰에서 "지난번과 비교" 질문에 "현재 저장된 과거 기록이 없어 직접 비교하기 어렵다"고 답함(과거 기록은 있으나, 모델 분석 창이 있으면 소리 크기 기반 비교를 하지 않는 설계라 비교할 지표가 없음. "기록이 없다"는 표현이 부정확함) |

검사 항목(모두 20/20): 폴백 없이 실제 Gemini 응답, 보낸 요청 기록, 규칙/데이터 분리, 인용 번호가 허용 범위 안, 후보 유무와 첫 문장 일치, 소리 크기 기반 "분당 N회" 문장 없음, 진단 단정 없음(진단을 거절하는 문장은 허용), 확인 없이 음악 제안 없음. 예외: 과거 기록을 부정하지 않음 19/20.

이 평가가 알려 주는 것: 수정 전에는 사용자에게 "질문에 답하는 척하지만 틀린" 답이 나갈 수 있었다. 이 평가가 알려 주지 않는 것: 실제 강아지 기록에서의 정확도, 사람이 읽었을 때의 답 품질, 문장별 수치 정확성.

## 확인 안 함

- 실제 반려견 기록으로 만든 설명의 정확도(합성·공개 음원 자료로만 확인).
- Gemini가 기록의 수치를 정확히 옮겼는지 문장별 검증.
- 귀가 설명 경로의 전송 내용 전수 캡처(외출 질문 경로는 `cloud_request`로 기록하도록 했으나 캡처 파일로 남기지는 않았다).
