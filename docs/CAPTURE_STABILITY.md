# 수집 안정성 보강과 시험 — 2026-10-23

대상: 노트북 웹캠·마이크 자동 수집(`scripts/capture_agent.py` → `scripts/monitor_audio_events.py`).

## 바꾼 것

| 문제 | 이전 | 이후 |
|---|---|---|
| 수집 프로그램(FFmpeg)이 죽음·장치 끊김 | 바로 `failed`로 외출 종료 | 에이전트가 5초·10초·…간격으로 최대 5번 재시작. 재시작 대기 중에도 heartbeat 전송(`starting` 표시). 60초 이상 정상 동작하면 횟수를 초기화. 5번 연속 실패하면 `failed` |
| FFmpeg는 살아 있는데 장치가 데이터를 안 줌 | 감지 못함 | 새 5초 구간이 30초 동안 나오지 않으면 수집 프로그램이 스스로 실패 처리 → 위 재시작 경로 |
| 백엔드 응답이 잠깐 끊김 | heartbeat 1회 실패에 수집 중지 | 연속 10회 실패해야 중지 |
| 카메라·마이크를 뽑았다 꽂음, 장치 이름 변경 | 같은 입력 인수로 재시작하다 5번째에 `failed` | `--redetect`(런처 기본): (재)시작 전마다 장치 목록을 다시 읽어 입력 JSON 갱신. 장치가 없으면 최대 5분 `starting`으로 기다리고(재시작 횟수에 세지 않음) 돌아오면 이어서 수집. 모드를 읽지 못하면(카메라 점유 중) 같은 장치 조합의 기존 640x480 30fps 입력을 유지 |
| `start_demo.ps1` 재실행 | 이전 에이전트가 종료되지 않고 쌓임(오래된 코드가 새 외출을 가져감) | 에이전트·수집 프로그램·캡처 FFmpeg를 명령줄로 찾아 함께 종료 |

재시작 사이의 공백은 외출 요약의 `미관찰` 시간으로 남는다. 조용했던 시간으로 해석하지 않는다.

## 시험 (노트북 웹캠·마이크, 공개 데모 DB)

두 번째 실행(첫 실행은 위 launcher 버그로 오래된 에이전트가 처리해 재시작이 일어나지 않았고, 원인을 고쳐 다시 시험함).

- 길이 600초 자동 관찰 외출. 150초·360초 부근에서 캡처 FFmpeg를 강제 종료.
- 두 번 모두 에이전트가 `capture program exited (1); restart 1/5`를 기록하고 수집이 이어졌다. 종료 뒤 상태는 `stopped`.
- 분석 표본 530.8초, 분석 창 118개, 미관찰 80.5초(시작 지연과 재시작 2회의 공백 포함).
- 자원: 파이썬 프로세스 합계 약 840~850MB, FFmpeg 약 122MB에서 10분간 증가 없음. 임시 영상 버퍼 4~6MB로 유지되고 종료 뒤 0MB.
- 시험 중 저장된 마이크 원본은 시험 뒤 모두 삭제했다. 관찰 수치는 남는다.

## 단위 시험

`tests/test_agent_supervision.py`: 충돌 후 재시작, 연속 충돌 시 포기, 장시간 정상 동작 후 횟수 초기화, 짧은 백엔드 단절 허용, 긴 단절 시 중지, 재연결 대기 중 중지 요청, 정지 감지 기준. 재탐지 시험(`tests/test_make_capture_input.py`, `RedetectTests`)을 더해 전체 Python 197개 통과, 10개 건너뜀.

## 아직 검증하지 않은 것

- 10분보다 긴 운용(수 시간). 메모리·디스크는 10분 동안만 관찰했다.
- 실제 USB 마이크·웹캠을 뽑았다 꽂는 경우. 재탐지는 FFmpeg 강제 종료 뒤 재시작(실장비, 입력 JSON·30fps 설정 유지 확인)과 `refresh()`의 장치 없음 판정(실제 FFmpeg로 확인), 대기·복귀 경로(단위 시험)로 나눠 검증했고, 물리적으로 뽑았다 꽂는 시험은 하지 않았다.
- 백엔드가 수십 초 이상 내려갔다 올라오는 경우의 실기 확인(단위 시험만 있음).
- 보관 기간 만료 삭제는 기존 백엔드 시험(`test_audio_clips`, `test_audio_training`, `test_event_videos`)으로 확인하며, 7일 경과 실기 확인은 하지 않았다.
